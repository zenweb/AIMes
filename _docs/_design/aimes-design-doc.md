# AIMes — Design Doc

## Problem Statement

工厂的产线管理员每天都在"救火"：设备故障、采集机宕机、工单延期、物料跟不上。现有 MES 系统（包括我们之前的 iMES）只是"记账式"的——记录发生了什么，但不会帮助预防问题。系统被"忍受"但不被"依赖"。

## Demand Evidence

之前 iMES 在真实工厂有部署和使用。产品建模、排程、BOM 变更会直接影响生产——用户在这些场景下表现出真实焦虑。但整体上 iMES 的附加值低，工厂只是为了"有比没有强"而在用。

## Status Quo

工厂目前用 iMES 开源版做基础数据记录。排产靠人工经验+Excel，设备数据采集不稳定（采集机经常死机），异常靠人去巡检发现。产线管理员是最大的痛点角色——每天到处救火，没有系统帮他提前发现问题。

## Target User & Narrowest Wedge

**产线管理员（总线管理员）**——管理全部产线，是最忙、最痛的角色。最小切入点：让系统能提前告诉他哪里要出问题，而不是等他去发现。排产排程是核心价值，AI 算法驱动、自我学习是长期差异化。

## Constraints

- 单人开发团队
- 开源 80% + 商业版 20%（AI 功能）的商业模式
- 需要同时支持 SaaS 和私有部署
- 技术栈：C# .NET 10 + Vue 3 + TypeScript + PostgreSQL（已完成 P0-P3 基础）

## Premises

1. AI 排产排程是核心价值主张，开源版做到 80%（不含 AI），商业版做完整 AI，系统自我学习、越用越准
2. 必须从"记账式 MES"升级到有预测和预防能力的系统
3. 开源版必须本身有足够价值，能吸引真实用户采用，不能是个空壳
4. 插件架构：标准化功能内置，非标准化功能通过插件扩展

## Cross-Model Perspective

**外部独立评审（Claude 子代理冷读）关键意见：**
- "Users tolerated it but didn't depend on it" 是整个项目的存在性威胁——每个功能必须通过"关了它会急吗"测试
- 插件架构在 pre-product 阶段是错的——先单体，等到有真实外部需求时再抽成插件
- 排程的 NP-hard 本质和 reward function 定义是最大未暴露风险——"AI 自我学习"跳过了一个根本问题：在优化什么？
- 48 小时原型建议：不做 CRUD，做一个实时预测甘特图，让产线管理员感受到"预测"的力量

## Approaches Considered

### 方案 A：插件架构优先（原计划）
- 从 0.1 版本就开始设计插件系统
- 风险：投入大、产出不确定、小团队难以维护

### 方案 B：单体优先 + 按需提取（推荐）
- 先做单体，当有真实外部用户需要扩展时再提取插件
- 优势：更快交付、更低复杂度

### 方案 C：聚焦排程 + 可观测性
- 把排程引擎和实时监控/预测作为第一优先级
- 插件架构推迟到商业版阶段

## Recommended Approach

方案 B + C 结合。先做单体、聚焦排程引擎和实时预警能力，让开源版本就有足够价值让工厂愿意试用。插件架构推迟到商业版阶段考虑。

## Open Questions

1. 开源版 80% 排程的边界：什么算"80%"？什么功能必须留到商业版？
2. 数据采集稳定性问题：采集机宕机的应对策略是什么？边缘计算？冗余？
3. 排程算法：第一阶段（开源）用什么启发式算法？性能目标是什么？
4. 多租户架构决策：SaaS 和私有部署如何共享代码库？

## Success Criteria

- 开源 6 个月后有 >=3 家工厂真实部署试用
- 产线管理员能说出"AIMes 让我少跑车间了"
- 商业版 AI 排程有足够用户数据开始训练
- 排程准确度随时间明显提升

## Distribution Plan

- 文档全面：快速开始、架构说明、API 参考
