## 缘起

2026-05-19 阅读《从"人跑流程"到"Agent指挥流程"：下一代企业数字化架构全景解析》，引发对 AIMes 战略方向的重新思考。

### 文章核心观点：三层架构

企业 AI 落地需要从"给人用的系统"转向"给机器协作的系统"：

1. **系统 CLI 化** — 把 ERP/CRM/OA 改造为机器可调用的标准化命令接口（不是回归终端，是构建机器操作协议）
2. **流程 Skill 化** — 把散落在制度、经验、群聊里的业务流程固化为可复用的"技能包"（触发条件 + 规则引擎 + CLI 编排 + 异常处理 + 反馈机制）
3. **员工 Agent 化** — 每个岗位配理解其职责、继承其权限的专属 Agent，员工从"跑流程的人"变为"指挥 Agent 的人"

### 关键行业证据（影响决策的几个）

- **固纬电子**：精密产线部署"智慧产线助理 Agentic AI"，插件不良返修率 **改善 50%** ← 制造业 Agent 落地的最直接数据点
- **百胜中国 Q睿**：餐厅运营 Agent 单一覆盖 20+ 场景 ← 单 Agent 容量参考
- **钉钉/飞书/企业微信**：相继开源官方 CLI ← 平台级 CLI 化已成共识
- **阿里"悟空"**：钉钉全面 CLI 化基础上的 Agent 平台 ← 平台路径的最高形态
- **Gartner AIR 框架**：记录系统 + 行动系统 + 智能系统 ← 与 CLI-Skill-Agent 同构，权威验证
- **毕马威 AI 就绪度报告**：70% 企业未做好 AI Ready ← 市场仍在早期

### 对 AIMes 的启示

文章方向对，但**实施路径有两种**：
- **平台化路径**（对标钉钉、阿里）→ 推迟到 v4
- **单点引爆路径**（对标固纬电子）→ **当前选择**

完整 13 行业案例 + 7 平台信号档案存于 [`ai-mes-future-vision.md`](ai-mes-future-vision.md#行业对标)。

## 一、战略定位

### 为什么是单点引爆，不是平台

参考的 [平台愿景路线图](ai-mes-future-vision.md)描绘了"从 MES 演示看板到 AI MES 指挥系统"的完整蓝图，包含 6 类岗位 Agent、MCP 协议、6 类角色工作台、低代码 Skill Builder。它在战略上没错，**但它需要一个团队和 12-24 个月的资源支撑**。

V1 当前是单人/小团队驱动。我们做了一个 CEO 视角的取舍：

```
平台路径（v4 愿景）          单点路径（本路线图）
────────────────────      ────────────────────
6 类 Agent 铺陈            1 个 Agent 打透
MCP 协议先发              不做协议，先做现金流
6 类工作台                1 个工作台
"AI MES 指挥系统"心智       "X% 交期达成改善"心智
卖概念                    卖数字
```

行业证据：固纬电子在精密产线部署"智慧产线助理"，以**插件不良返修率改善 50%**做出了行业级数据点。我们要复刻这个范式，但场景换成排产。

### 单点的精确定义

**Agent**：调度员 Agent
**Skill**：排产优化 Skill（事件触发 → 多策略生成 → 推荐 → 人审核 → 采纳/拒绝 → 效果回写）
**主指标**：交期达成率 ↑（On-Time Delivery Rate, OTD）
**销售故事**："我们的调度员 Agent 把交期达成率提升了 X%"

为什么是这套组合：
- V1 现有最强的领域——规则排程引擎已经实现 EDD / SPT / WSPT / 瓶颈优先 / 最小换型 / 物料优先 / 平衡交付，多策略候选已具备
- V1 已有 `AdoptionFeedbackService` 做排程采纳反馈——直接复用为 Skill 反馈机制
- V1 已有 `AiDecisionTrace` 做决策追溯——直接复用为 Agent 决策审计
- 交期达成率是所有制造业老板听得懂的语言，跨业务场景通用
- EDD/WSPT 策略本来就直接对该指标优化，Agent 推荐天然服务于这个目标

## 三、主指标 — 交期达成率量化框架

### 定义

```
OTD = (按期完工的工单数 / 总工单数) × 100%
```

按期完工：实际完工时间 ≤ 工单承诺交期。

### 基线对比框架（本路线图核心新增）

这是平台愿景完全缺失但 C 路线必须有的：

```
┌─────────────────────────────────────────────────┐
│  基线（人工排产）           Agent 推荐           │
│  ────────────────          ────────────────     │
│  按经验/启发式排序           多策略候选 + 推荐    │
│  无解释                      解释 + 影响分析       │
│  无效果回写                  采纳→实绩回写        │
│                                                 │
│        OTD_baseline   vs   OTD_agent             │
│              ↓                  ↓                │
│              ───────── A/B ─────────             │
│                       │                          │
│              ΔOTD = (OTD_agent - OTD_baseline)   │
│              改善百分比 = ΔOTD / OTD_baseline    │
└─────────────────────────────────────────────────┘
```

### 实现要点

1. **基线策略**：在演示数据集上模拟"无 Agent"的人工排产策略——可以是简单 FCFS 或固定单一策略（如纯 EDD）
2. **A/B 对比**：同一批工单分别用基线和 Agent 推荐策略排程，记录两组 OTD
3. **效果回写**：采纳 Agent 方案的工单实际执行结果回写（可以是模拟执行 + 干扰注入），形成"建议→实际"对比表
4. **可信度护栏**：
   - 工单数 ≥ 30 单（避免小样本偏差）
   - 至少 3 种冲突场景（正常 / 插单 / 设备故障）
   - 每种场景多次跑（蒙特卡洛模拟），取均值与置信区间
   - 报表给出"在 N 工单 / M 场景下，OTD 改善 X% (±Y%)"

### 验证有效性的反向问题

> "如果 OTD 改善是噪音，我们怎么发现？"

护栏：
- 同一基线跑多次，看噪音范围
- Agent 推荐被人工拒绝率 > 30% → 推荐质量有问题，OTD 改善不算数
- ΔOTD 在 95% 置信区间下不显著 → 报告时明确标注"不显著"，而不是吹嘘数字

这是平台愿景完全没有的——本路线图把"如何避免吹牛"内置到设计里。

## 四、双轨标杆数据

### 轨道 1：Demo A/B（4-8 周内出货）

**目标**：在演示数据集上跑出可信的 A/B 对比报告，作为销售材料。

**产物**：
- 公开演示数据集（30+ 工单，3+ 冲突场景）
- A/B 对比报告（含置信区间、噪音分析、场景拆解）
- 可一键重跑的脚本（任何人下载 V1 都能复现）
- README + 官网首屏的"X% 交期达成改善（演示数据）"标语

**坦白**：明确标注"基于演示数据集，现场数据请联系 POC"——可信度上限是"实验室级"，但下限是"可复现且可审计"。

### 轨道 2：POC 工厂（3-6 个月，并行启动）

**目标**：找一家愿意合作的小中型制造商做 POC，跑出真实环境数据。

**启动动作**（不等 demo 完成）：
- 立即开始客户漏斗：行业人脉 / 制造业社群 / 既有联系人
- 准备 POC 提案模板（含部署成本、合作条款、数据使用权）
- 低折扣甚至免费部署，换取"数据使用权 + 案例公开权"
- 候选优先级：多品种小批量 + 插单频繁 + 数据基础好（MES/ERP 已有数据流）

**风险护栏**：
- 不预设"X% 改善"目标，让数据自己说话
- 即使现场数据改善小于 demo（很常见），仍可作为"在真实环境下验证 Agent 推荐落地"的案例

### 双轨为什么互为补强

```
Demo A/B（4-8 周）  ──→ 销售材料 ──→ POC 客户招募材料
                                              ↓
                                     POC 工厂（3-6 月）
                                              ↓
                                     现场数据 ──→ 升级销售材料
```

Demo 是期权变现金流的桥，POC 是现金流的源。两个不启动则永远没有现场数据。

## 五、Phase A / B / C 划分

### Phase A（2026Q3，约 4 周）：单点闭环最小可行版

**目标**：调度员 Agent 跑通完整闭环。

**做什么**：
- 调度员 Agent 事件订阅（基于 V1 现有 SignalR + 后端事件）
- 排产优化 Skill 内嵌封装（不抽 SkillRegistry，直接 hardcode）
- Agent 方案面板前端（基于 v0.1.0 已有甘特图扩展，不做整套工作台）
- 采纳/拒绝写入 `AdoptionFeedbackService`（已有，加 Agent 标记字段）
- Agent 决策写入 `AiDecisionTrace`（已有，加业务键）
- Agent 操作审计扩展 `AuditLog`（增加 `InitiatedBy=Agent` 字段）

**不做**：
- ~~6 类 Agent 任何一个的雏形~~
- ~~SkillRegistry / AgentRuntime~~
- ~~MCP Server~~
- ~~多 Agent 通信~~
- ~~异常闭环 / 质量闭环 / 设备闭环~~
- ~~除调度员外的角色工作台~~

**验收**：
- 一个完整工单从触发到 Agent 推荐到人采纳到效果回写跑通
- 测试覆盖：3 种场景（正常 / 插单 / 设备故障）的端到端用例
- 演示视频 ≤ 5 分钟能讲完单 Agent 故事

### Phase B（2026Q4，约 4 周）：业务指标量化框架

**目标**：把"X% 交期达成改善"做出可信、可复现、可审计。

**做什么**：
- 演示数据集扩展：30+ 工单 / 3+ 场景 / 8+ 设备 / 替代料
- 基线策略实现（FCFS / 纯 EDD / 启发式）
- A/B 对比框架（同一批工单两组运行，记录指标）
- 蒙特卡洛模拟脚本（多次运行取均值与置信区间）
- A/B 对比报告生成器（输出 Markdown + 图表）
- README / 官网首屏更新（"X% (±Y%) 交期达成改善 - 演示数据"）

**不做**：
- ~~工厂部署~~（这是 Phase C）
- ~~产品化包装~~（先把数字做扎实再说）

**验收**：
- A/B 报告可一键重跑
- ΔOTD 在 95% 置信区间下显著（如果不显著，报告标注"不显著"，不吹嘘）
- 第三方下载 V1 后能在 30 分钟内复现报告

### Phase C（2027Q1-Q2，约 3-6 个月）：标杆案例

**目标**：找 1 家工厂部署，跑出现场数据。

**做什么**：
- POC 客户漏斗（在 Phase A 启动时就开始）
- 部署适配（POC 客户现场环境兼容）
- 现场数据采集 / 对比 / 报告
- 案例公开（征得客户同意）

**不做**：
- ~~多客户铺开~~（先做透 1 个）
- ~~SaaS 化~~（先做透 self-hosted）

**验收**：
- 1 个公开案例，含客户名（征得同意）+ 现场指标
- 案例内容能放在官网 + 销售材料

## 六、关键风险与护栏

### 风险 1：单点不够独立成产品

**症状**：单 Agent 跑通但客户说"我已经有 APS 了，加你这个值不值不知道"
**护栏**：
- demo 数据上的 OTD 改善 X% 必须显著（≥10%，否则继续优化）
- POC 工厂选择标准：现有无 APS 或 APS 不好用的，避开有强 APS 的客户

### 风险 2：演示数据集"数据集训练" - Agent 在真实环境失效

**症状**：demo 数据完美，POC 工厂跑出来差距大
**护栏**：
- demo 数据集冲突场景必须包含"真实工厂的脏数据"（缺料、信息滞后、人工干预）
- Phase A 完成后立即启动 Phase C 漏斗，不等 demo 完美再去找客户

### 风险 3：POC 客户找不到

**症状**：3 个月没有候选客户上钩
**护栏**：
- 不只靠人脉漏斗，同时投放制造业社群 / 行业会议 / 内容营销
- 提供"免费 + 数据使用权交换"模式降低决策门槛
- 失败回退方案：开源版扩散 + 数据更扎实（更多场景 / 更多模拟），用 demo 数据做行业话题

### 风险 4：被平台愿景拖回平台路径

**症状**：写代码时想"反正 SkillRegistry 也快要做，不如先做了"
**护栏**：
- 本路线图是当前唯一执行口径，平台愿景仅供 v4 参考
- 任何超出"调度员 Agent + 排产优化 Skill + 量化框架"范围的 PR 必须显式说明为何"为本路线图服务"，不能只说"为平台愿景服务"

| **使用场景** | 单点验证完成后做扩张设计参考 | Phase A/B/C 实施依据 |

**重要**：平台愿景不是"错的"，是"目前不该做的"。等本路线图跑出 POC 现场数据，证明了 Agent 单点价值，**那时回到平台愿景续接扩张**才是正确动作。

## 八、行业对标（保留并聚焦）

### 直接对标：固纬电子智慧产线助理

> **关键事实**：在精密仪器产线部署 Agentic AI，将"插件不良返修率"改善 **50%**。
>
> **对本路线图的启示**：这是单点 Agent 在制造业落地的最直接证据。我们的目标是用调度员 Agent + 交期达成率做出同等性质的数据点。

### 类比对标：百胜中国 Q睿

> **关键事实**：餐厅营运 Agent，单 Agent 覆盖 20+ 场景。
>
> **对本路线图的启示**：单 Agent 容量不应低估。调度员 Agent 当前只做排产优化，但单点足够深时，单 Agent 可吸收更多场景（v4 扩展空间）。

### 反向对标：阿里"悟空" / 钉钉 CLI 化

> **关键事实**：平台级 CLI 化，让 Agent 原生操作上千能力。
>
> **对本路线图的启示**：这是 v4 的方向，**不是当前的方向**。我们当前不做平台，v4 验证后再做。
